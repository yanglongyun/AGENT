# 0.1.0 — 合并成单一 Web 客户端

前面九个版本里长出了四个「宿主」:`web`、`desktop`、`os`、`rule`。
这一版把它们收成一个产品:**一个 Web Agent**。

## 一、为什么要合

复制整个包来做探索,是个好手法 —— `os` 和 `rule` 都是这么来的,
主线全程没被弄坏过。但探索完不收,代价会立刻显形。合并前实测:

```text
ai/ ↔ rule/ai          0 处差异        767 行逐字节相同的死拷贝
web/ui/src ↔ os/ui/src        25 个文件里 19 个完全相同
web/ui/src ↔ rule/web/ui/src  25 个文件里 17 个完全相同
```

README 里那句「`ai` 与 `agent` 在仓库中始终只有一份」当时已经是假的。

真正的理由不是洁癖。0.0.9 修过一个 bug:`~/Downloads/**` 不匹配 `~/Downloads` 自身,
`rm -rf` 整个目录反而漏过。**这类代码复制三份,就意味着修一处、忘两处。**
普通功能抄三遍最多是烦,权限抄三遍是事故。

## 二、结构:按层,不按桶

```text
AGENT/
├── ai/       模型循环 + 协议驱动     不知道工具,不知道界面
├── agent/    工具 + 压缩 + 权限引擎   不知道 HTTP
├── server/   HTTP · SQLite · SSE · 轮次 · 问询通道 · 应用宿主
├── shared/   事件名契约
├── ui/       React 客户端(唯一一份)
├── apps/     用户的应用
└── test/  .dev/  scripts/  config.js
```

七个顶层目录,每个都有一句话能说清是什么。

**没有 `features/` 这类桶。** 桶名不排除任何东西 —— 每个目录都是 feature,
所以这个名字什么都不表达,一开口子,以后放不下的都往里扔,两年后它就是第二个 `utils/`。

权限和请示因此不占目录,按层拆开各归各位:

```text
agent/danger.js rules.js permission.js     引擎
agent/functions/consult.js                 请示,和 bash / read 并列的普通工具
server/approvals.js                        问询通道 —— 权限和请示共用,所以在这层
ui/src/permission/                          档位标、规则面板、审批坞、请示卡
```

`consult` 原本是「可整体删除的扩展目录」。目标定成一个产品之后不再需要那个性质:
它的可选性体现在**界面上那个勾选框**,不是文件系统的目录边界。
顺带把一条歪的依赖掰直了 —— 原先 `consult` 借 `permission.ask`,是 feature 依赖 feature。

## 三、没有建 `shell/`

只有一个交付方式时,`shell/` 是个空壳。`server/index.js` 就是入口。
等 Desktop 真回来再拆,那时它才有第二个成员。

**产品定位是 Web**:打包桌面端门槛高,而 Web 既能本地跑也能整个部署到服务器。

## 四、删掉了什么

```text
os/  rule/  web/  desktop/  dist/     内容已全部并入或不再需要
electron / electron-builder            开发依赖
config.js 里的 web / os / rule 三段     合成一段 client
```

仓库从 836M 降到 86M(其中 78M 是 `ui/node_modules`)。

`web/` 留到最后才删:合并期间需要一个已知能跑的东西作对照。
新客户端在浏览器里验证通过之后才动它。

## 五、合并前必须先做的一件事

**补测试。** 匹配引擎在 0.0.9 里是零覆盖的,而它决定「一次删除会不会被拦下来」——
这种代码的失效是静默的:规则看着在列表里,实际一次都没命中过。

`test/permission.test.js`,17 个用例,专门锁住两条曾经出过事的:

- `X/**` 必须罩住 `X` 自身(`rm -rf ~/Downloads` 曾经漏过)
- 没有问询通道时当场拒绝,不挂起(悬着的 Promise 会把整轮永远挂住)

没有这一步,合并合坏了不会有人知道。

## 六、合并后的验证

| | |
|---|---|
| 应用 | 懒启动,`notes` 自有 SQLite 读写正常 |
| 权限 | 规则编译成 `动作 delete · 路径 ~/Downloads/**` |
| 注入 | 规则和应用清单**同时**进 `instructions` |
| 界面 | 侧边栏应用组 + 输入框权限标,同一个界面 |
| 回归 | 73 个测试通过 |

## 七、留给下一版

- 注入给模型的文本里带着「(没有拦截条件兜底,全靠你自觉遵守)」——
  这句是写给用户看的,不该写给模型看,等于明着告诉它「这条没人管你」。
- 规则的排序目前不影响判定(所有规则的结果都一样是「问」),
  上下移只是排列。要么给它真实语义,要么去掉。
- 助理提议规则(`suggest_rule`)还没做。新模型下它天然安全 ——
  规则只可能导致更多询问,不可能减少。
