# 0.3.0 — 让标准活起来

0.2.0 把契约写完并两轮打磨(外部评审、场景反推)。这一版换方向:**不再打磨文本**。

## 一、为什么

标准的迭代有个不对称性:**加东西便宜,改东西致命**。所以第一版的职责只有两条 ——
把改不动的钉对,让真实使用开始。前者已经完成(SPEC「稳定性分级」里"已稳定"那六条);
后者是这一版的全部内容。

纸面推演的产出在递减:busy 那个坑不是想出来的,是删反代的副作用撞出来的。
HTTP/1.0 没有 Host 头,MCP 第一版只有三种原语 —— 标准从来不是设计完善后发布的,
是被真实使用磨出来的。完备主义的终点是 XHTML:完美、严格、没人用。

> **v1 的胜负手:3~5 个每天真被使用的 app 存在。**
> 「AI 能造出来」已经验收过(倒数日);现在要证明的是「造出来的东西有人天天用」。

## 二、这一版做什么

1. **造 3~5 个日用 app**。判据只有一条:自己每天真的会打开。
   便签和倒数日是示范,不算数 —— 要的是那种不打开会难受的东西。
   候选方向(待定,用真需求挑):剪贴板暂存 / 每日待办 / 项目看板 /
   常用命令面板 / 阅读稍后 —— 或者完全不在此列的、你本来就缺的工具
2. **摩擦日志**:`.dev/0.3.0/friction.md`,只追加。每次造 app 或用 app 时
   觉得别扭的地方,一行记下,不当场修 —— 攒起来看分布,v2 从这份清单长出来,
   不从想象长出来
3. **AI 造 app 保持绿**:每次动宿主或 SPEC 后,「AI 从零造一个 app 并跑通」
   这条验收要重跑。它是标准的可用性测试,红了就是标准或注入的提示词坏了

## 三、欠账登记(不属于这一版,但别丢)

从 0.2.0 各轮评审攒下的已知问题,按严重度:

1. **内部面对本机进程无鉴权** —— app 后端可 curl /api/* 拿别的 app 的 token、
   读设置、驱动 agent。app 间隔离目前是君子协定(SPEC 信任模型里已如实写明)。
   正解:宿主 UI 会话密钥。多用户与公网鉴权同属这一刀
2. `/host/ai/agent` 的 SSE 无心跳,长轮次经反代可能被掐
3. notify 的 badge 落成 toast,侧边栏角标未做
4. 权限模型采纳 Triforge 1.3.0 的护盾两态(盾开/盾关,砍「逐步确认」)——
   已评审认可,含出厂规则种子的决策,待排期

第 1 条什么时候做:出现以下任一信号就立刻 —— 要公开分发、要多用户部署、
或第一个不是自己写的 app 进来。在那之前,日用 app 优先。
