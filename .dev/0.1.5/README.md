# 0.1.5 — 提议

补 0.1.4 留下的两个缺口。原则不变:不扩一堆规则管理工具,只加一个工具。

## 一、规则的分组:试了两版,都拆了

起因是真实的:桌面目录下同时放着多个项目,有的上线了必须考虑兼容,有的在开发考虑兼容就是污染代码,
一张单子管不了。为此走了两版:

1. **规则加作用域。** 规则默认全局,可选挂一个项目名,对话标项目。做完发现它把集合藏在一个字段里,
   表达不出"我可以保存一份、创建一份"。
2. **手册。** 两张表,对话指向一本手册,像对话指向工作目录;没有全局,常用的那本就是「通用」。
   后端和数据没问题,问题出在界面:手册的切换、改名、复制、删除,加上里面的规则,
   怎么排都是一个塞满管理动作的面板。做了三套原型(主从两栏、文档式、快切弹出加独立页),
   又做了一套"约定住在对话顶上"的方向,再做了一套三档加标签行的 —— 每一套都在给手册找地方放。

最后的决定:**不分组,回到一张全局的规则单。** 分组的需求是真的,但它带来的界面复杂度
超过了它解决的问题;这个项目探讨的是实现,不是替用户管项目。项目之间的差异,先靠
在对话里说一句、靠 propose 记进单子再停用来对付,等真痛了再回来。

代码回到 0.1.4 的形态:`rules(id, text, enabled, position, created_at)`,settings 里一个 `rulesEnabled`。
两版分组的代码全部删掉,不留字段。原型文件留在本目录,`permission-panel.html` 是最后那套。

## 二、提议:模型往用户面前放一个可选项

三种形式都讨论过:

- **弹卡确认**:你刚说完"不留兼容",它立刻弹卡问"要记吗"。这是刚砍掉的"要不要继续"换了个地方。
- **直接改、可撤销**:信任模型,结果摆在明处。但改错的规则会静默地影响之后每一轮。
- **弱打扰、不阻塞**:模型提了就走,提议挂在输入框上方,用户点勾生效、点叉丢掉,不点就一直在。

选第三种。提议不是弹窗,因为它不等答案;也不是擅自落库,因为点了才生效。

提议不只服务规则。它是一个通道:**模型把一个可选项放到用户面前,点了才发生**。
第一版两种:

| kind | 提议条上显示 | 点勾 |
|---|---|---|
| `rule` | 记成规则:… / 规则 3 → … | 落进规则表 |
| `prompt` | 下一步:…? | 原文填进输入框,用户可以改了再发 |

只能落成这两种结果。凡是点了会直接产生副作用的(执行命令、发请求)不走这里 ——
那是带延迟的弹窗,而且更危险,点的时候上下文已经过去了。需要答案才能继续的,是 confirm,阻塞。

### 工具

```
propose({ kind: 'rule' | 'prompt', text, replaces? })
  text      规则原文,或建议的下一句话;kind=rule 时为空表示删掉 replaces 指的那条
  replaces  要改的规则编号;不给就是新增,记进对话当前用的那本手册
```

执行器把提议存进 `proposals` 表,广播,立刻返回"已提议,等用户决定"。模型不等。
下一轮提示词里规则单已经是新的,它自然知道结果。

### 边界写进提示词,不加机制

- rule:只记跨对话还成立的话。"这个文件用四空格"不记,"不加署名"记。能并进已有规则的用 replaces 改,不新开。
- prompt:只在真的存在一个需要用户拍板的分叉时提,顺理成章的下一步不提,一次最多一条。
  这种最容易泛滥,一泛滥用户会连 rule 提议一起无视。
- 拿不准这句话是不是长期偏好,不调工具,在回复里问一句。那是对话,不是弹窗。

### 存储

`proposals(id, conversation_id, kind, text, replaces, created_at)`。
不设超时,它不卡任何东西。同一条规则被提议两次,后一次覆盖前一次。对话删了,提议一起删。

### confirm 卡上那个勾

删掉。confirm 只问"这件事能不能做",规则的沉淀归 propose。

## 三、落地时的几个决定

- **编号在提示词里,id 在库里。** 模型用 `[3]` 指代规则,提议通道在轮次开始时握着这一轮的规则列表,
  把编号换成 id 再存。提议存的是 id,规则单之后怎么变,提议指的还是那一条。
- **提议通道和问询通道一样,由宿主给。** `runAgent` 多一个 `propose` 参数,给了才把 propose 工具发给模型;
  app 触发的轮次和停用规则的轮次都不给 rule 提议。agent 层照旧不认识提议存哪、怎么显示。
- **接受时可以改文。** 提议条上的原文是输入框,勾之前能改;点勾把改过的文本送去落库。
- **prompt 提议的接受只是撤下。** 填输入框是界面的事,走现成的 `seedDraft`,服务端不参与。
- confirm 工具的 `suggestion` 字段和卡上"记成规则"的勾删掉,归 propose。

## 四、要动的

- 表:新表 `proposals`。
- server:rulesSection 带编号;proposals 列出 / 接受 / 丢弃三个端点;events 加 PROPOSAL_ASK / PROPOSAL_DONE。
- agent:tools.js 加 propose 定义,functions/propose.js 执行器,runner 装配,提示词加一段。
- UI:输入框上方的提议条;confirm 卡去掉那个勾。

## 五、压缩时机:从轮开头挪进每次请求前

原来只在一轮开头看一次水位,依据是上一轮结束时存的 usage。工具循环一轮能跑三十次请求,
上下文在一轮之内就能撑爆,那时候没有任何压缩介入,模型直接报超限,整轮死掉,
这一轮的水位也没存下来。

改法就三处,和口头说的一样:

1. **模型每次应答回来就存 usage。** 循环把 usage 挂在那次应答的最后一个 item 上 emit 出去,
   runs.js 收到就 `saveUsage`。轮子中途死掉,下一轮也知道涨到哪了。
2. **每次请求前判断。** 循环直接调 `agent/compact.js`,压缩配置由宿主注入;每次请求前看一眼
   最近一次应答的 usage,超线就压。第一次请求前用库里的。压了就 emit 一个 `compact` 事件,
   宿主据此记 seq 区间、广播。压缩属于循环:工具结果是在循环里进上下文的,判断只能在这里。
3. **压完接着用压缩后的上下文。** 循环持有一个可替换的 `context`,钩子返回什么就用什么往下走;
   不再是"传进来的历史 + 新产生的"两个只增数组每次重拼。结束时返回最终 `context`,runs.js 直接存。

配对不用特殊处理:切点选法本来就保证 function_call 和它的 output 同在尾段,第几轮触发都一样。
compactions 表的 seq 记账也统一了:上下文最后一项永远是最近落库的那条,尾段之前的最后一个
seq = 最新 seq - 尾段条数。
